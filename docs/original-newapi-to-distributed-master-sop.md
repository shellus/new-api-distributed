# 原版 New API 切换至 newapi-distributed master SOP

本文是生产执行清单，用于把上游兼容的原版 New API 切换为 newapi-distributed 的 master 入口，并在验收失败时恢复冻结的原版镜像。

数据迁移原理、Schema 变化和演练结论见 [Master 数据切换与回滚](./distributed-master-switch.md)。分布式控制面和 edge 节点不在本次首次切换范围内。

## 切换原则

- 原版和 master 复用现有 PostgreSQL、Redis 与应用数据目录，不复制在线数据库目录。
- 首次切换保持 `EDGE_DISTRIBUTED_ENABLED=false`，只验证 master 对原版入口的兼容性。
- 原版镜像和 master 镜像都以镜像 ID 固定，不依赖可变标签判断版本。
- 停写后先运行不具备正式服务网络别名的 master 候选容器；候选验证通过后才重建正式服务。
- 普通回滚继续使用同一数据库，不自动执行 `pg_restore`。
- 所有真实路径、镜像标签、账号、端口和 Compose 项目名只写入权限为 `0600` 的私有环境文件。

## 角色与中止权限

一次切换至少需要明确以下职责：

- 执行人：运行预检、切换和回滚命令，保存脚本输出；
- 验收人：验证登录、API、计费、日志和配套服务；
- 决策人：在验收失败或观察到数据异常时决定回滚；
- 通知负责人：维护停写窗口和恢复通知。

执行人和决策人都可以在正式服务重建前中止。master 已对外提供流量后，任何数据或计费异常都应先停止写入，再判断回滚。

## 阶段一：发布准备

### 1. 完成功能对齐

设置 `MASTER_PARITY_APPROVED=YES` 前必须确认：

- 现网原版分支中要求继续保留的本地功能和修复已同步到 master；
- 审计上报、对话归集字段、任务计费和视频直链等现网能力已完成回归，或已由决策人明确接受下线并从验收清单移除；
- 相关后端测试、竞态测试、静态检查和前端构建通过；
- master 保留原版入口的 API、认证、计费和管理后台行为。

未完成任一项时不得通过人工门禁。

### 2. 准备不可变镜像

- 使用项目 Dockerfile 构建正式 master 镜像；
- 记录 `docker image inspect` 返回的完整镜像 ID；
- 将该 ID 写入私有环境文件的 `EXPECTED_MASTER_IMAGE_ID`；
- 确认私有环境文件中的 master 标签解析到同一镜像 ID；
- 保留当前正在运行的原版镜像，切换脚本还会在停写前再次冻结并记录其真实 ID。

### 3. 声明停写范围

私有环境文件中的 `QUIESCE_SERVICES` 必须包含所有可能修改主库或日志表的服务，例如：

- 正式 New API 服务；
- 订阅结算或对账服务；
- 自动充值或余额调整服务；
- 会写入渠道、用户、额度、日志或任务表的配套程序。

只读服务不需要停止。无法确认某个配套服务是否写库时，按写入者处理。

### 4. 完成克隆演练

在生产切换前，使用在线 PostgreSQL 的一致性逻辑快照执行完整演练：

```bash
SWITCH_ENV_FILE=/private/drill.env \
ops/master-switch/drill.sh all
```

演练必须得到 `result=passed`，并确认原版、master、回滚原版三个阶段的业务指标一致。

## 阶段二：切换前预检

在维护窗口开始前执行只读预检：

```bash
CUTOVER_ENV_FILE=/private/cutover.env \
ops/master-switch/cutover.sh preflight
```

预检必须确认：

- Docker 与 Compose 可用；
- master 镜像 ID 与期望值完全一致；
- Compose override 已清除原服务的 `build` 配置；
- 正式应用和 PostgreSQL 正在运行；
- 主业务库和日志库使用同一 PostgreSQL；
- 当前 `quota_data.model_name` 数据长度允许原版回滚；
- 备份目录至少有脚本要求的可用空间；
- 私有环境文件权限没有向组或其他用户开放。

预检失败时不得进入停写阶段。

## 阶段三：执行切换

### 1. 开始维护窗口

- 发布维护通知；
- 暂停人工改价、充值、渠道调整和其他管理操作；
- 确认验收人和决策人在线；
- 保存切换前的容器状态和监控基线。

### 2. 运行切换命令

```bash
CONFIRM_PRODUCTION_SWITCH=YES \
MASTER_PARITY_APPROVED=YES \
CUTOVER_ENV_FILE=/private/cutover.env \
ops/master-switch/cutover.sh cutover
```

脚本依次执行：

1. 重跑预检并固定 master 镜像 ID；
2. 冻结当前原版容器的真实镜像；
3. 停止 `QUIESCE_SERVICES` 中的全部写入者；
4. 生成并验证停写状态下的 PostgreSQL custom-format 快照；
5. 记录切换前业务指标；
6. 启动隔离的 master 候选容器并执行 Schema 迁移；
7. 检查候选镜像 ID、网络别名、健康状态、Schema 和业务指标；
8. 删除候选容器，使用相同 master 镜像重建正式服务；
9. 恢复 `RESUME_SERVICES` 中的配套服务并记录当前活动镜像。

候选验证或正式启动失败时，脚本会尝试恢复冻结的原版镜像。仍需由执行人检查原版健康状态和业务指标，不应只依赖退出码判断恢复完成。

## 阶段四：master 验收

首次切换仍保持分布式控制面关闭。以下项目全部通过后才结束维护窗口：

### 服务与管理功能

- `/api/status` 和容器健康检查正常；
- 管理员登录、普通用户登录和会话续期正常；
- 用户、令牌、渠道、分组、订阅和日志页面可以读取；
- Redis 连接正常，没有持续的数据库或缓存错误；
- 配套写入服务已恢复且没有重启循环。

### API 与计费

- 使用测试令牌完成一次非流式文本请求；
- 使用测试令牌完成一次流式文本请求；
- 请求身份、渠道选择、模型映射和上游响应正常；
- 用户额度、令牌额度、渠道用量和消费日志只扣减一次；
- 日志中的模型、分组、渠道、token 数和金额符合请求；
- 任务类接口完成创建、查询、结算和结果地址验证；
- 现网审计上报和对话归集仍能收到预期字段。

### 数据与日志

- master Schema 门禁全部通过；
- 没有批量额度变化、负数计费或重复消费日志；
- 没有持续出现数据库迁移、唯一索引、outbox 或结算错误；
- 切换前后的核心业务总量差异只能来自验收请求和恢复后的真实流量。

验收通过后发布恢复通知，并保留原版镜像、停写快照和切换状态文件，直到观察窗口结束。

## 回滚触发条件

出现以下任一情况，应停止继续验收并进入回滚判断：

- 正式 master 无法保持健康或持续重启；
- 登录、令牌认证或主要 API 出现系统性失败；
- 额度、订阅、计费或日志出现重复、负数或无法解释的变化；
- 审计、任务结算或现网特有功能缺失；
- 数据库迁移未完成，或出现持续的 Schema/索引错误；
- 配套服务无法在 master 下恢复；
- 监控指标明显偏离切换前基线且无法快速定位。

业务影响不明确时，优先停止写入，避免在分析期间继续扩大账务差异。

## 执行回滚

首次切换尚未启用 edge 时执行：

```bash
CONFIRM_PRODUCTION_ROLLBACK=YES \
CUTOVER_ENV_FILE=/private/cutover.env \
ops/master-switch/cutover.sh rollback
```

脚本会：

1. 停止 master 和全部写入者；
2. 检查模型名长度和 edge 结算阻塞项；
3. 记录回滚前业务指标；
4. 启动不具备正式网络别名的原版候选容器；
5. 比较原版候选与回滚前业务指标；
6. 使用冻结的原版镜像重建正式服务；
7. 恢复配套服务并记录当前活动镜像。

回滚后需要重复执行服务、登录、API、计费和日志验收。master 新增的表和列会保留，原版会忽略它们；原版 AutoMigrate 可能把 `quota_data.model_name` 缩回 64。

## 已启用 edge 后的额外回滚步骤

真实 edge 流量发生后，不得直接执行镜像回滚。必须先：

1. 从外部入口停止 edge 新请求准入；
2. 等待所有节点在途请求完成；
3. 上传所有节点本地结算 block 和消费日志 outbox；
4. 确认 master 已接受并发布全部结算数据；
5. 确认没有非终态租约、资金预留、未发布日志或处理中回执；
6. 确认所有 edge 节点已停止或与 master 隔离；
7. 设置 `CONFIRM_EDGE_NODES_DRAINED=YES` 后再执行回滚。

master 数据库中的阻塞项为零不能证明远端节点本地队列为空，远端 drain 必须单独确认。

## 备份恢复边界

镜像回滚是正常恢复路径。停写快照仅用于同库数据已经损坏、原版也无法正常读取时的灾难恢复。

执行 `pg_restore` 前必须：

- 停止所有数据库写入者；
- 保存当前故障库的额外快照；
- 校验目标备份的 SHA-256 和归档目录；
- 明确备份之后的真实业务写入将丢失；
- 由决策人确认重建目标数据库。

不得把在线 PostgreSQL 数据目录的文件复制当作一致性备份，也不得在普通镜像回滚时自动覆盖数据库。

## 完成记录

一次切换完成后应保存以下非敏感结果：

- 原版和 master 的完整镜像 ID；
- 预检、切换、验收和回滚结果；
- 停写快照文件名及 SHA-256；
- 业务指标比较结果；
- 维护窗口开始、恢复或回滚的时间；
- 未完成门禁和后续处理负责人。

真实环境路径、域名、账号、端口和凭证继续保存在私有环境文件或运维系统中，不写入项目文档。
